# HippoWiki – Users and Login

The users and login feature as built: HippoWiki can only be used after logging in with a user name and a password.
Every account is of one of two types, chosen when it is created and never changed: an admin manages the accounts and
sees no content, a user works with the folders, tabs and pages and manages no accounts. The first admin is created on
the first start; admins create all other accounts, and every account sets its own password at the first login. What a
user sees and does with a folder depends on the user's role on it (see `folder-roles.md`).

Code: `src/features/users/` (the accounts), `src/features/auth/` (login, logout, the session, the login wait, the
password changes, logging out other browsers and the check of the own password for the consent page), `src/lib/auth.ts` (the Better Auth instance), `src/lib/client-address.ts`,
`src/lib/password-hash.ts`, `src/proxy.ts`, `scripts/admin.ts`, `scripts/common-passwords.ts` and the routes
`src/app/login/`, `src/app/change-password/` and `src/app/users/`. The models are `User`, `Account`, `Session`,
`Verification`, `AuthSecret`, `LoginAttempt` and `LoginWindow` in `prisma/schema.prisma`; the first four have the shape
that Better Auth and its `username` plugin expect. The admin setup in the container image is described in `container-image.md`.

The connected apps of a user and the own account page `/account` are described in `connected-apps.md`.

Tests: `e2e/login.spec.ts`, `e2e/change-password.spec.ts`, `e2e/own-password-change.spec.ts`,
`e2e/log-out-other-browsers.spec.ts`, `e2e/users.spec.ts`, `e2e/access.spec.ts`,
`integration/auth-service.test.ts`, `integration/user-service.test.ts`, and the unit tests next to the code, such as
`src/features/auth/service.test.ts`, `src/features/auth/wait.test.ts`, `src/features/users/schema.test.ts`,
`src/features/users/user-type.test.ts`, `src/features/users/common-passwords.test.ts`, `src/lib/addresses.test.ts`
and `src/lib/client-address.test.ts`.

## User names and email

- A user name follows the name rule of folders, tabs and pages (`src/lib/names.ts`), so it can be part of an address
  as it is. It is 3 to 30 characters long and unique. Surrounding spaces are removed. The rules are in
  `src/features/users/schema.ts`, the lengths in `src/features/users/limits.ts`.
- Each user gets a hidden placeholder email in the reserved domain `.invalid`, because Better Auth needs an email
  address. It is never shown and no mail is sent.
- Users are written with Prisma, not through the sign-up of Better Auth, which stays disabled.
  `src/features/users/records.ts` is the one place that knows the shape of the rows of a user; an integration test logs
  in through Better Auth with such a user, so a change of the shape in a later Better Auth version is noticed.

## Passwords

- A password is 8 to 128 characters long, counted as the length of the string, as Better Auth counts it
  (`src/features/users/limits.ts`). The upper limit protects the password hashing from very long inputs.
- Any characters are allowed, spaces and non-Latin letters included. Nothing is trimmed or normalised, and there are no
  composition rules such as "must contain a digit".
- A new password must not be built only from the user name or a context word, plus digits and symbols. The context
  words are `hippowiki`, `hippo`, `wiki` and `admin` (`PASSWORD_CONTEXT_WORDS` in `src/features/users/schema.ts`).
  Case does not count: with the user name and the context words removed, a password must keep at least one letter.
  So `hippowiki2026`, `Alexander1` for the user `alexander` and `admin-admin!` are refused, while `admin-password` and
  `wikipedia1` are accepted.
- A new password must not be one of the 10,000 most common passwords that meet the length rule, in any case. The list
  is `src/features/users/common-passwords.ts`, generated by `scripts/common-passwords.ts` from a SecLists file of
  breach data (MIT licence), pinned to one commit; `README.md` has the command that makes it again. It is checked on
  the server only and never reaches the browser.
- A new password must differ from the current one and is entered twice. The rules on new passwords apply to the forced
  password change and to the admin setup; existing passwords and those of the seed are not checked again.
- A password is never logged, and only its hash is stored.
- Passwords are hashed with Argon2id at the minimum settings of OWASP (`src/lib/password-hash.ts`). Better Auth handles
  the login, the sessions and the logout; only its password hashing is replaced.
- One server process runs only a few hashes at the same time; further callers wait in the order they came and give up
  after a while. A login, password change or user creation that gives up is answered as busy: a user creation or
  password change writes nothing, and a login is not counted (see "Failed logins").

## Account types

- Every account has exactly one type, `admin` or `user` (the column `type` of `User`; `isAdmin()` in
  `src/features/users/user-type.ts` is the one place that decides it). The type, not the name, decides what an account
  may do.
- An admin logs in, changes the own first password, sees the user list and creates accounts of either type. An admin
  sees no tab, page or deleted page, and connects no apps (see `content-structure.md` and `connected-apps.md`). An admin
  sees the names of the folders and who has which role on them on the overview `/folder-roles`, but never has a role,
  changes no role and creates no folder (see `folder-roles.md`).
- A user logs in, changes the own first password, and sees and changes the folders, tabs, pages and deleted pages as far
  as the role on each folder allows, creates folders, holds connected apps and uses the wiki through MCP. A user sees
  the user list but creates no accounts.
- The type is chosen when an account is created and never changes, by anyone and in any way: no page, form, dialog,
  tool or command offers to change it, and a trigger of the migration `prisma/migrations/20261116103037_init/` refuses every update of the database that
  changes it. A person who needs both jobs has two accounts.
- There can be any number of admins. Every admin manages the accounts like the first one.
- Admin tasks are done only in the browser, with the session of an admin: no admin task is reachable through MCP or a
  token, at any MCP address, now or later (see `mcp.md`).

## Admin setup

- The admin setup (`scripts/admin.ts`, `ensureAdmin()` in `src/features/users/service.ts`) creates the first admin,
  named `admin`, with the password from `HIPPOWIKI_ADMIN_PASSWORD` when no account of that name exists, as a first
  password that must be changed at the first login. When an account named `admin` exists, it does nothing, its type
  included, and does not look at the password; changing the variable later does not change the password. Later
  admins may have any valid user name.
- A missing or invalid password creates nothing, and the setup fails. The password follows the rules of "Passwords",
  with `admin` as the user name, so a common password or one such as `admin2026` is refused. A value in angle
  brackets, such as the `<first password>` of the README, counts as invalid: it is a placeholder (`adminPasswordSchema`
  in `src/features/users/schema.ts`). `.env.example` leaves the variable empty, so that no public value can become the
  password of the admin. Two setups at the same time create one admin.
- Only the admin setup reads `HIPPOWIKI_ADMIN_PASSWORD`; the server never does.
- In development it runs as `npm run admin:setup`; in the container image on every start (see `container-image.md`).

## Login and logout

- Users log in at `/login` with a user name and a password. There is no self-sign-up, no "forgot password" link and
  no mail.
- A login leads a user to `/folders` or to the address it was asked for (see "The way back after a login"), and an
  admin to `/users`, or to the password change when it is pending. Who is logged in and opens `/login` is led there
  as well, and `/` leads a user to `/folders` and an admin to `/users`.
- An unknown user name and a wrong password get the same answer, and both compute one hash, so nobody can find out
  which names exist. A name that breaks the name rule and a password longer than a password may be cannot belong to
  a user; they are answered like a wrong password, without a hash.
- The header shows "Folders" for a user, "Users" for every account, "Folder roles" for an admin, the name of the
  logged-in user, which links to the own account `/account`, and "Log out", a plain form that works without
  JavaScript. An admin has no "Folders".
  Logging out ends the session of the browser and leads to the login page; the other sessions of the user stay. The
  own account `/account` has "Change password" and "Log out other browsers" for every account (see "Own password
  change" and "Logging out other browsers").
- After a login and a logout every route is revalidated, so that the header and cached pages follow the new session.
- Better Auth is called only on the server. Its route handler is not mounted, so there is no `/api/auth/...` and no
  public endpoint to sign up or to sign in past the login wait.

## Sessions

- A session lasts 30 days from the login (`SESSION_LIFETIME_SECONDS` in `src/lib/auth.ts`) and is not extended by
  use. Every check of a session reads the database, so
  an ended session is refused at once.
- A user can have several sessions at the same time, one per browser.
- The session cookie cannot be read by scripts (`HttpOnly`), is sent with same-site requests and top-level navigations
  only (`SameSite=Lax`) and is `Secure` when `NODE_ENV` is `production`. Browsers keep `Secure` cookies on `localhost`
  as well.
- The secret that signs the cookies is generated on first use and stored in `AuthSecret`; processes that start
  together sign with the same one. There is no variable for the secret. The login needs no public address of the
  wiki either: the optional `HIPPOWIKI_PUBLIC_URL` is for the MCP server and OAuth (see `container-image.md`).

## The way back after a login

- A read without a session cookie is sent to `/login?next=<path and query>` by `src/proxy.ts`, and the login leads
  back to that address. Other requests, such as a submitted form, and Server Actions are sent to `/login` without a
  way back, because their address may not be one to read.
- With a first password the login leads to `/change-password?next=…`, and the change leads on to the address.
- `next` is accepted only as a path on this site: it starts with exactly one `/`, not with `//` or `/\`, has no
  control characters and is at most 2048 characters long. Anything else leads to `/folders`, so that a crafted link
  to the login page cannot send a user who just logged in to another site. The rule is `safeNextPath()` in
  `src/lib/addresses.ts`; the login page, the password change and both actions check the value again.
- An admin sees no content, so for an admin a way back to `/` or to an address under `/folders` or `/deleted-pages`,
  judged by its path, leads to `/users` instead of the not-found page; every other way back stays. The rule is
  `landingPath()` in `src/lib/addresses.ts`, used by the login, the password change and both of their pages.
- The folder list is where a login leads anyway, so it is left out of the address.
- `requireUser()` redirects without a way back, unless its caller passes one: only the consent page of OAuth does
  (see `oauth.md`). A request with a session cookie that is no longer valid therefore leads to `/folders` after the
  login, except from that page.
- `next` is not an action and not a view: it opens nothing on the login page.

## Failed logins

Two limits hold back the guessing of passwords; their numbers are defined in `src/features/auth/wait.ts`. A login is
refused while either of them asks for a wait. The current password of a password change and the password on the
consent page of OAuth are counted the same way, as a login of the name of the session user from the client address
group of the request (see "Forced password change" and `oauth.md`):

- Per user name and client address group: after 5 failed logins in a row for a name from one group, the next login
  for that name from that group has to wait 1 minute. Each further failure doubles the wait, up to 15 minutes.
  Failures more than 24 hours apart are not in a row.
- Per user name alone: at most 20 logins are counted per name and hour, from all groups together. The hour starts with
  the first login that is counted; a further login waits until the hour is over, and the login after that starts a new
  hour.

What a user and an operator can rely on:

- A login during a wait is refused with the longer of the two waits, without checking the password and without being
  counted. The log line says which limit asked for the wait. A password change and an approval on the consent page
  that have to wait are refused the same way, with the wording "Too many wrong passwords" instead of "Too many failed
  logins", because they are not logins.
- Every other login is counted in both limits before its password is checked, or in neither. Logins at the same time
  therefore get no more guesses than logins one after another: 5 per group, one more after each wait, and 20 per name
  and hour. The others are refused with the wait, whatever their password.
- A login that cannot be counted, because the database fails or the counts keep changing under logins at the same
  time, is answered with the general error, without checking the password.
- A successful login forgets the count of its name and group and the hour of its name. The counts of the name from
  other groups stay.
- A login whose password was not checked, because the hashing was busy or something failed, takes its counts back, so
  that a wait that was over does not start again.
- An unknown name is counted and has to wait like a known one. A name that breaks the name rule is not counted,
  because it cannot belong to a user and the tables would otherwise take any text.
- A password longer than a password may be, for a valid name, counts as a failure.
- The counts are stored in the database, so they survive a restart of the server. Counts that no wait needs any more
  are deleted by later logins.
- How the counting works (conditional writes, the retries, taking a count back, the deleting) is described in
  `src/features/auth/service.ts`.

The client address group (`clientAddressGroup()` in `src/lib/client-address.ts`):

- The actions of the login, of the password changes and of "Approve" on the consent page read it from the headers of
  the request, in the same way (`src/features/auth/client-address.ts`), because `/login` does not pass
  `src/proxy.ts`, and pass it to the auth service as a plain argument.
- With `HIPPOWIKI_TRUSTED_PROXIES=0`, the default, no header is read and every login is in the group `shared`: the
  wait then counts per user name alone.
- With `HIPPOWIKI_TRUSTED_PROXIES=n`, the group comes from the n-th entry from the right of `X-Forwarded-For`, the
  address that the outermost trusted reverse proxy saw. The leftmost entry is never used, because a client can write
  it. `X-Real-Ip` and `Forwarded` are never read. What the environment has to provide for this is described in
  `container-image.md`.
- An entry that is missing or not an address puts the login into `shared`, and the action logs a warning with the
  reason, without the value of the header. A login never goes uncounted because its address is unknown.
- An IPv4 address is its own group. An IPv6 address is in the group of its /64, because one customer controls at least
  that many addresses; an IPv4-mapped IPv6 address counts as its IPv4 address.
- The service trusts no caller: a value that is not a group as `client-address.ts` writes them counts in `shared`, and
  an error is logged.
- Every log line of a login has the group next to the name, and the line of a successful login names the user as
  well. The line of a logout names the user of the session that ended.

## Authenticated access only

Nothing can be read or changed without a login. Only the login page and `/api/health` are public for a browser. The
MCP addresses of the folders under `/mcp/` ask for a bearer token instead of a session (see `mcp.md`), and the endpoints that an OAuth
client calls before it has a token show nothing of the wiki (see `oauth.md`). The login is checked in two layers, as
the authentication guide of Next.js describes:

- `src/proxy.ts` sends every request without a session cookie to the login page, without asking the database. Only the
  login page, `/api/health`, `/mcp` and the addresses below it, the public endpoints of OAuth and the static files of Next.js (`/_next/static/`)
  pass it; `/_next/image` is behind the login like every other address, and answers 404 with a session, because the
  image optimizer of Next.js is switched off. A Server Action called without the cookie leads to the login page as
  well, with a full page load instead of the error page.
- `requireUser()` in `src/features/auth/session.ts` checks the session in the database. Every page behind the login,
  every query and every Server Action calls it first; it is the layer that protects the data. Without a session it
  leads to the login page, and while the first password is pending, to the password change. Pages call it before they
  read the query string, so that an invalid address also leads to the login page. The exceptions, among them the
  login and the logout and the consent page of OAuth, are listed with their reasons in "Reads and writes" and "Login
  and sessions" of `architecture.md`.
- An address that does not exist stays "not found" for everyone who has a session cookie.
- `not-found.tsx`, `error.tsx` and `global-error.tsx` show no data and have no check. Without a user the header shows
  no menu.

## Forced password change

- Whoever logs in with a first password, the admin after the admin setup and every new user, must set a password of
  their own at `/change-password` before doing anything else. Every other address leads there; logging out stays
  possible. The header shows the name and "Log out", but no menu, and the name is no link, because the own account
  would only lead to the password change.
- The form asks for the current password, the new one and its repetition, by the password rules above.
- A wrong current password counts as a failed login of the user name from the client address group of the request,
  and a right one like a successful login (see "Failed logins"). During a wait the change is refused at the current
  password with its own wording, "Too many wrong passwords", without checking it. A new password that breaks a rule is
  refused before the current password is checked, and is not counted.
- The change ends all sessions of the user and starts a new one for the browser that made the change, so the other
  browsers of the user are logged out.
- The pending change is cleared only after the password has changed. If that fails, the user changes the password once
  more.
- After the change a user lands on `/folders` and an admin on `/users`, or on the address the login was asked for (see
  "The way back after a login"). Who has no pending change and opens `/change-password` is led there too.

## Own password change

- Every account changes its own password at any time after the forced password change, in the dialog "Change
  password" of `/account` at `?action=change-password`, with the current password, the new one and its repetition, by
  the password rules above. A user whose first password is still pending is led to the forced change first.
- The change ends all other sessions of the account and starts a new one for the browser that made it: the other
  browsers are logged out at their next request, and this one stays logged in.
- The current password is counted like a login of the user name from the client address group of the request (see
  "Failed logins"); a new password that breaks a rule is refused before the current password is checked, and is not
  counted. A refused current password, wrong or during a wait, empties the password fields.
- A user with at least one connected app can choose "Also disconnect all my apps", not ticked when the dialog opens. An
  admin, a user without apps and every user while OAuth is off see no such choice; one that is sent anyway is ignored
  and logged as a warning.
- The apps are disconnected only once the password is changed and the other sessions are ended, so that they are
  never lost without a change. When disconnecting them fails, the change stands, the failure is logged, and `/account`
  asks the user to revoke the apps in the list.
- After the change `/account` says that the password was changed and the other browsers were logged out, and, when
  chosen, whether the apps were disconnected. The notice is shown once: a reload shows no message.
- While the password hashing is busy, the change is answered as busy and changes nothing.
- The change is logged as an info line with the user id, the user name, whether the apps were disconnected and how
  many; never a password.

## Logging out other browsers

- "Log out other browsers" on `/account` opens a confirmation at `?action=log-out-others`. Confirming ends all other
  sessions of the account without changing the password; the current browser stays logged in, and no password is
  asked. Closing the dialog ends nothing.
- After it `/account` says that the other browsers were logged out, also when there was no other session. The notice
  is shown once.
- When the sessions cannot be ended, the dialog stays open with an error that says that the other browsers may still
  be logged in; nothing claims success, and the failure is logged.
- It is logged as an info line with the user id, the user name and how many sessions were ended.

## User list and creating users

- Every account sees the user list, at `/users`, from the header entry "Users": every account, admins included, by
  name, with its type and the time it was created. Only an admin also sees whose password change is pending, because
  that marks the accounts that still use a generated first password; for a user it is not even read.
- Only an admin creates accounts, in the "New user" dialog at `/users?action=create`, and only an admin sees the
  button "New user". For a user the address of the dialog is not found, and a crafted request creates nothing.
- The admin enters a user name and chooses the type, "User" or "Admin", with "User" chosen when the dialog opens; the
  dialog says that the type cannot be changed later. A request that names no type or an unknown one is refused with
  an error at the type, and nothing is created; no type is chosen in its place.
- HippoWiki generates a first password and shows it exactly once, with the name and the type, for the admin to pass
  on. The new account has to change it at the first login.
- The log line of a new account names its user name, its type and the admin who created it, never the password.
- A generated password is 20 characters long (`FIRST_PASSWORD_LENGTH` in `src/features/users/password.ts`), drawn
  from a cryptographic random source from letters and digits that are not easy to confuse.
- The password is not part of an address or of a stored page, and it is gone after a reload. The dialog closes only
  through its link back to the user list, so that it cannot be lost by a stray click.
- A form cannot choose the password or skip the password change: only the name and the type are read.
- No user name has to be reserved for an address of its own, so `/users/<name>` stays free for every valid name.

## Routes

- `/login`: the login form. Public. `?next=<path>` is the address the login leads to.
- `/change-password`: the forced password change. It needs a session; without a pending change it leads on as a login
  does. `?next=<path>` is the address the change leads to.
- `/users`: the user list, for every account, with the action `create` for the "New user" dialog, for admins only.
- `/account`: the own account (see `connected-apps.md`). Its actions `change-password` and `log-out-others` open the
  dialogs of "Own password change" and "Logging out other browsers" for every account, and `?notice=<notice>` reports
  once what one of them did; a notice with an action or an unknown one shows the not-found page.
- None of the first three has views, and only `/users` has an action; any other action or view shows the not-found
  page.

## Decisions

- Two features: `users` writes accounts with Prisma and the password hashing and does not use Better Auth; `auth` is
  the only code that uses Better Auth, through `getAuth()`. A lint rule keeps `@/lib/auth` to the auth service and
  `src/lib/`.
- A login is counted with conditional writes of the Prisma client, repeated when another login got in between,
  instead of one SQL statement that checks the wait and counts: the rules of the waits stay in `wait.ts` alone and are
  not written a second time in SQL.
- The two counts of a login are written in one interactive transaction, so that a login is counted in both limits or
  in neither and no login slips past one of them.
- The limit per user name is an hour window and not a count of failures in a row. One address gets 5 guesses at once
  and then one more after each wait, so it would reach 20 failures in a row after about 3 hours and could then hold a
  wait for the name with one request every 15 minutes. In one hour a single address manages 11 counted logins at most,
  and 4 per hour after that, so it never fills the window.
- The wait is counted per user name and client address group, so the owner of an account does not share a wait with a
  stranger who guesses its password. The limit per name alone keeps a bound on the guesses for an account, however
  many addresses they come from.
- The client address comes from a number of trusted reverse proxies (`HIPPOWIKI_TRUSTED_PROXIES`), not from a list of
  their addresses: Next.js never shows the application the address of the connecting peer, so a list could not be
  checked anyway. Without the setting, no header is read.
- The actions read the client address and the service takes the group as a plain argument, as it takes the
  `Headers`: the service stays free of forwarding headers and of the configuration of the deployment.
- New passwords are checked against a bundled list of common passwords instead of an online service such as Have I
  Been Pwned: no request leaves the server, the check works offline and in every deployment, and the list is drawn
  from breach data. 10,000 entries are a fraction of what an online check knows, which is why the online check stays
  a candidate (see "Current limits").
- The context rule refuses passwords built only from a context word, not every password that contains one: a rule on
  "contains" would also refuse `admin-password` or `wikipedia1`, whose other letters make them no easier to guess than
  any other phrase, and would act like a composition rule. A password of digits only contains no word to remove and is
  left to the list, so that there is still no composition rule.
- An account is never disabled after many failures, unlike NIST SP 800-63B-4 asks after 100 failures in a row: with
  no mail and no password reset there would be no way back in.
- Two types of account, so that whoever manages the accounts does not get access to the content on the way. An admin
  sees no content, as the cleanest line between running the wiki and reading it. With folder roles an admin sees the
  folder names and who has which role on them, on an overview of its own, so that whoever manages the accounts can
  tell who has access to what, but never gets a role (see `folder-roles.md`). Rejected: an admin who sees the folder
  list without its contents.
- The type is fixed at the creation, so that no account can gain or lose access to the content or to the management of
  accounts later on: an admin cannot make an account a user to read the content, and a user can never be raised to an
  admin. The database refuses a change as well, so that no code and no command can make one. Rejected: changing the
  type in the user list.
- The first admin keeps the fixed name `admin`, which ASVS 6.3.2 counts as a default account, so that the setup still
  needs only `HIPPOWIKI_ADMIN_PASSWORD`; the type, not the name, decides what an account may do. The name would not
  stay secret anyway: every account sees the user list. What makes a default account dangerous does not apply: there
  is no default password, the setup fails without one, and the first password must be changed at the first login.
  Guesses for `admin` are held back by the waits of "Failed logins" like those for any other name. The risk accepted
  is that every installation has a known name to guess and to lock out (see "Current limits"). Rejected: a setting for
  the name of the first admin.
- An admin starts on the user list, the only page with work for an admin, also when the login carries a way back to
  the content, so that the login does not end on the not-found page. Rejected: starting on `/account`, and following
  the way back to the not-found page.
- Every account sees the user list with the types, so that users know who works in the wiki and whom to ask for an
  account; it is the same page for both types, so that there is one list to keep. Users see name, type and creation
  time, but not whose password change is pending. Accepted: every user sees every login name, admins included; the
  waits of "Failed logins" hold back guesses for any name. Rejected: a user list for admins only, a separate page for
  users, and the same columns as admins.
- The "New user" dialog preselects "User", because most accounts are users and an admin is then created on purpose. A
  request without a type or with an unknown one is refused instead of creating a user, so that a broken or crafted
  request is noticed. Rejected: no preselection, and falling back to "User".
- The log names the type of a new account and the admin who created it, so that a new admin is easy to spot.
- A container needs `DATABASE_URL` and `HIPPOWIKI_ADMIN_PASSWORD` and nothing else, so the secret of the session
  cookies is stored in the database instead of a variable.
- Who is calling is found out in the adapters, from the session cookie. What the caller may do is checked in the
  services: every function that depends on the type takes the acting user, with its type, as its first argument and
  decides itself (`isAdmin()` in `src/features/users/user-type.ts`). A session whose user has no known type is
  treated like a missing session.
- The auth service takes the `Headers` of the request as an argument, because the session lives in a cookie. `Headers`
  is a web standard and not part of Next.js, so the service still works outside a request of Next.js. The functions
  that change the session also return the response headers that set or clear the cookie. In a Server Action the
  `nextCookies()` plugin of Better Auth has already applied them; a caller outside Next.js, such as the integration
  tests, passes them on itself.
- Better Auth logs through the pino logger, and only its errors. Its warnings repeat a refused login, which the auth
  service logs itself with the user name, or say that no base URL is set, which is on purpose: Better Auth uses it
  for its HTTP handler and for links in mails, and HippoWiki has neither.
- A logout that fails throws and shows the error page, because the button has no place for a message and a session
  that could not be ended must not look ended.
- A change of the own password always ends the other sessions; disconnecting the apps is the user's choice, because a
  routine change should not force every app to be connected again. The choice is not ticked and is shown only to a
  user with apps, so that a routine change keeps the apps and nobody sees a choice that does nothing. Rejected: ticked
  by default, and shown to every user.
- The password change and the logout of other browsers are dialogs of `/account` at addresses of their own, like
  "Revoke app", so that the page stays short and the dialogs can be linked. Rejected: a form always shown on the page,
  and a page of its own.
- Wrong passwords at both password changes and on the consent page count against the waits of the login, so that a
  stolen session gives no more guesses than the login page does, and a right one counts like a successful login, so
  that the three forms behave alike. Rejected: also ending the session after 5 wrong passwords, a count of its own,
  and letting only the login forget the count.
- Because of that, someone who guesses the password of a user at the login also makes the user's own password change
  wait, with `HIPPOWIKI_TRUSTED_PROXIES=0` from anywhere, up to 15 minutes or the rest of the hour. This is accepted:
  the guesser does not know the password, the sessions of the user keep working, and logging out the other browsers
  needs no password. Rejected: letting a session pass the waits of the login, which needs a count per session.
- A wait at a password change and on the consent page has its own wording, "Too many wrong passwords", because it is
  not a login. Rejected: the wording of the login.
- Logging out the other browsers asks for a confirmation but not for the password, because ending sessions only
  protects the account. Rejected: ending them at one click, and asking for the password.
- After a change or a logout of the other browsers, `/account` says what happened, once. Rejected: leading to the start
  page like the forced change, and closing the dialog without a message.
- When disconnecting the apps fails after the password was changed, the change stands and the user is told to revoke
  the apps, because a changed password and logged-out browsers are the more urgent part. Rejected: disconnecting the
  apps first, which could lose them without a change.
- A failure to log out the other browsers is shown in the dialog, not on the error page as a failed logout: the current
  browser is still logged in and can try again, and the message does not claim that anything ended. Rejected: the
  error page.
- The other sessions are deleted by the auth service in one write that leaves out the current session, not with
  `revokeOtherSessions` of Better Auth: that returns no number, deletes the sessions one by one, and Better Auth was
  found to swallow a failed delete at the logout, so a failure could look like success.
- The password changes and the logout of other browsers are logged with the user and the counts, so that an operator
  can follow what happened to an account; the line of a login names the user and the group, and the line of a logout
  the user.
- The seed and the tests have a known admin and a known user (`prisma/known-users.ts`), both with the password change
  already done. The seed upserts them by name, because an admin that `npm run admin:setup` created has another id, and
  sets the type only when it creates one. The sample content has the known user as its last editor.

## Current limits

- no groups of users for folder roles: every role is given to one user (see `folder-roles.md`)
- no change of the type of an account; a person who needs the other type gets a second account
- no public content: nothing can be read without a login (see "Public content" in `roadmap.md`)
- no way to reset a lost password of an admin; for now the only way is a change directly in the database or a second
  admin who creates a new account
- no password reset by an admin for other accounts, so a lost first password cannot be replaced
- no filter of the user list
- a password change ends the connected apps of the user only when the user chooses so at the change of the own
  password; the forced password change never does (see `connected-apps.md`)
- an admin cannot end the sessions or the connected apps of another account; for now the only way is a change
  directly in the database
- no list of the own sessions: a user can only log out all other browsers at once
- no deactivating or deleting of users; deactivating, when it comes, must also stop the user's connected apps and decide
  what happens to a folder whose last Owner it concerns (see `folder-roles.md`). A user who has edited content or has
  a role cannot be deleted for good at all, because the keys from content to its last editor, from a page revision to
  its user and from a role to its user restrict deleting (`onDelete: Restrict`, see `content-structure.md`). The
  history of a page keeps the name of every user who changed it for as long as the page exists, which a later
  deletion of users has to take into account (see `page-history.md`)
- no expiry of first passwords
- no online check of new passwords against breached passwords, only the bundled list (see "Breached password check"
  in `roadmap.md`)
- no page for each user; content records only its last editor (see `content-structure.md`), not who created it
- no mail, no TOTP, no passkeys, no sign-in with other providers
- while the hour of a name is full, the right password is refused as well. Roughly 10 to 20 address groups that work
  together, or 4 unused ones every hour, can keep a name locked most of the time; a routed IPv6 /48 or a botnet
  provides them. Closing this needs a budget of its own for clients that have logged in before, see `roadmap.md`.
- no limit on logins per client address across user names; that is a task of the reverse proxy
- the group of an IPv6 address is always its /64; there is no setting for the prefix
- no audit log
- no browser client of Better Auth, and its HTTP handler is not mounted
- no switch for session cookies without `Secure`: a production build needs HTTPS in front of it, or `localhost`
- a password change is not atomic: Better Auth ends the sessions, stores the password and starts the new session in
  separate statements; after them the forced change clears the flag, and the own change disconnects the apps when
  chosen
