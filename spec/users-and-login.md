# HippoWiki – Users and Login

The users and login feature as built: HippoWiki can only be used after logging in with a user name and a password.
One admin account is created on the first start; the admin creates and lists all other accounts, and every account
sets its own password at the first login. Everyone who is logged in can read and change all content; there are no
rights yet.

Code: `src/features/users/` (the accounts), `src/features/auth/` (login, logout, the session, the login wait and the
forced password change), `src/lib/auth.ts`, `src/lib/password-hash.ts`, `src/proxy.ts`, `scripts/admin.ts` and the
routes `src/app/login/`, `src/app/change-password/` and `src/app/users/`. The admin setup in the container image is
described in `container-image.md`.

## Model

In `prisma/schema.prisma`. `User`, `Session`, `Account` and `Verification` have the shape that Better Auth expects for
its core tables and its `username` plugin, adapted to the conventions of the other models: UUID ids generated by
PostgreSQL and `timestamptz(3)` for all times.

- `User`: a user account
  - `username`: the user name, unique. The column is required, although the plugin declares it optional.
  - `name`: Better Auth needs a display name; it is always the same as `username`.
  - `email`: the hidden placeholder address (see "User names and email"), unique
  - `mustChangePassword`: whether the user still has the first password; true by default
  - `emailVerified`, `image`, `displayUsername`: fields of Better Auth that HippoWiki does not use
  - `createdAt`, `updatedAt`: timestamps
- `Account`: the way a user logs in. Every user has exactly one, the credential account: `providerId` is `credential`,
  `accountId` is the id of the user, and `password` holds the encoded Argon2id hash. It is deleted with its user.
- `Session`: a login of a user in one browser, with the `token` of the session cookie and `expiresAt`. It is deleted
  with its user.
- `Verification`: a table that Better Auth expects; no feature of HippoWiki writes it.
- `AuthSecret`: the secret that signs the session cookies, in a single row (`id` is always 1; a check constraint that
  the migration adds by hand allows no other row).
- `LoginAttempt`: the failed logins in a row for a submitted user name, with `username` as its key, `failures` and
  `lastFailedAt`. It has no relation to `User`, because unknown names are counted too.

The admin is the user named `admin`. There is no role column.

## User names and email

Defined in `src/features/users/schema.ts`:

- A user name follows the name rule of folders, tabs and pages in `content-structure.md`: lowercase letters and digits
  in groups joined by single hyphens. It can therefore be part of an address as it is.
- It is 3 to 30 characters long, the limits of the `username` plugin. The rule replaces the character check of the
  plugin.
- User names are unique. A taken name shows "Name is already in use".
- Surrounding spaces are removed from a name that a form or a caller submits.
- Each user gets the hidden placeholder email `<name>@users.hippowiki.invalid`, because Better Auth needs an email
  address. `.invalid` is a reserved domain; the address is never shown and no mail is sent.
- Users are written with Prisma, not through the sign-up of Better Auth, which stays disabled.
  `src/features/users/records.ts` is the one place that knows the shape of the two rows; the users service, the seed
  and the test helpers use it. An integration test logs in through Better Auth with such a user, so a change of the
  shape in a later Better Auth version is noticed.

## Passwords

- A password is 8 to 128 characters long. The upper limit protects the password hashing from very long inputs.
- The length is the length of the string, as Better Auth counts it. It is checked with a refinement on that length,
  not with `.min()` and `.max()` of Zod, which count code points: with two measures a password of emoji could pass
  one check and fail the other.
- Any characters are allowed, spaces and non-Latin letters included. Nothing is trimmed or normalised.
- There are no composition rules such as "must contain a digit".
- A password must not be the same as the user name.
- A new password must differ from the current one and is entered twice.
- A password is never logged, and only its hash is stored.

## Password hashing

In `src/lib/password-hash.ts`, with `hashPassword()` and `verifyPassword()`:

- Argon2id from `@node-rs/argon2`, with the minimum settings of OWASP: 19 MiB of memory, 2 iterations and 1 lane. The
  settings are named in the code instead of relying on the defaults of the package.
- Better Auth keeps handling login, sessions, the session cookie and logout. Only its password hashing is replaced,
  through its `emailAndPassword.password.hash` and `verify` options.
- One server process runs at most 4 hashes at the same time. Further logins, password changes and user creations wait
  for a free slot, in the order they came.
- A caller that has not got a slot after 10 seconds gives up with `PasswordHashBusyError` and takes no slot later. The
  services turn the error into the code `busy`, which the forms show as "Too many logins at the moment, please try
  again".
- A slot is freed when its hash has ended, also when it failed.
- The limiter lives on `globalThis`, so that a module that is evaluated twice still shares it.

## Admin account and setup

- There is exactly one admin account, named `admin`. The admin can see and change all content like every other user,
  and is the only one who lists and creates users.
- `ensureAdmin(password)` in `src/features/users/service.ts` creates it:
  - If a user named `admin` exists, it does nothing and does not look at the password.
  - Otherwise it checks the password against the password rules, hashes it and creates the admin with a pending
    password change.
  - A missing or invalid password creates nothing. Two calls at the same time create one admin: the second one finds
    the name taken and counts that as "exists".
- `scripts/admin.ts` is the entry of the admin setup. It reads `HIPPOWIKI_ADMIN_PASSWORD`, prints one line for
  "created" or "exists, nothing to do" and exits with 0; for a missing or invalid password and for every other failure
  it prints a message to the error output and exits with 1. It is the only code that reads the variable: it is not
  part of `serverEnvSchema`, and the server never reads it.
- In development it runs as `npm run admin:setup`, which loads `.env` when the file exists. In the container image it
  is bundled into one file and run by `image-admin.sh` on every start (see `container-image.md`).
- Once the admin exists, the variable is ignored; changing it later does not change the password.

## Login and logout

- Users log in at `/login` with a user name and a password. There is no self-sign-up, no "forgot password" link and
  no mail.
- A login leads to `/folders`, or to the password change when it is pending. A user who is logged in and opens
  `/login` is led there as well.
- An unknown user name and a wrong password get the same answer, "Invalid user name or password", and both compute one
  hash, so nobody can find out which names exist. After a failed login the form keeps the name and empties the
  password.
- A name that breaks the name rule and a password of more than 128 characters cannot belong to a user; they are
  answered like a wrong password, without a hash.
- The header shows the name of the logged-in user and "Log out", a plain form that works without JavaScript. Logging
  out ends the session of the browser and leads to the login page; the other sessions of the user stay.
- After a login and a logout every route is revalidated (`revalidatePath("/", "layout")`), so that the header and the
  pages the browser has cached follow the new session.
- Better Auth is called only on the server, as `auth.api` from the auth service. Its route handler is not mounted, so
  there is no `/api/auth/...` and no public endpoint to sign up or to sign in past the login wait.

## Sessions

- A session lasts 30 days from the login and is not extended by use: Better Auth never refreshes it, and its cookie
  cache stays off, so every check of a session reads the database.
- A user can have several sessions at the same time, one per browser.
- The session cookie cannot be read by scripts (`HttpOnly`), is sent with same-site requests and top-level
  navigations only (`SameSite=Lax`) and lasts 30 days. It is `Secure` when `NODE_ENV` is `production`: the browser
  reaches the wiki over HTTPS through the reverse proxy of the environment, while the container keeps speaking plain
  HTTP. Browsers also keep `Secure` cookies on `localhost`.
- The secret that signs the cookies is 32 random bytes, generated on first use and stored in `AuthSecret`. When two
  processes start together, the row that was inserted first wins and both sign with it. There is no variable for the
  secret and none for the public address of the wiki.
- `getAuth()` in `src/lib/auth.ts` creates the single Better Auth instance on first use and keeps it for the process,
  like the client of `getDb()`. Nothing happens on import, because `npm run build` runs without a database.

## Failed logins

- After 5 failed logins in a row for a user name, the next login for that name has to wait 1 minute. Each further
  failure doubles the wait, up to 15 minutes (`src/features/auth/wait.ts`).
- A login during the wait is refused with "Too many failed logins. Please try again in N minutes.", without checking
  the password and without counting the attempt.
- A successful login deletes the count of its name.
- The count is stored in `LoginAttempt`, so it survives a restart of the server. A failure is counted in one statement
  that also creates the row.
- An unknown name is counted and has to wait like a known one. A name that breaks the name rule gets no row, because
  it cannot belong to a user and the table would otherwise take any text.
- A password of more than 128 characters for a valid name counts as a failure.
- A login that is refused because the password hashing is busy or because of an error is not counted.

## Authenticated access only

Nothing can be read or changed without a login. Only the login page and `/api/health` are public. The login is checked
in two layers, as the authentication guide of Next.js describes:

- `src/proxy.ts` sends every request without a session cookie to the login page. It only looks whether the cookie is
  there, with the helper of `better-auth/cookies`, and does not ask the database.
  - Its matcher leaves out the login page, `/api/health` and the static files of Next.js.
  - A Server Action that the client of Next.js calls without the cookie, for example a form submitted after a logout
    in another tab, is answered the way Next.js answers an action that redirects to another site: with the address of
    the login page in the header `x-action-redirect`, which the client opens with a full page load. An HTTP redirect
    would make the client show the error page. The proxy recognises such a request by its `next-action` header. Both
    headers are internals of Next.js; an end-to-end test covers them.
  - Every other request that is not a read is redirected with 303, so that the browser asks for the login page with
    `GET`.
- `requireUser()` in `src/features/auth/session.ts` checks the session in the database. Every page, every query and
  every Server Action calls it first; it is the layer that protects the data.
  - Without a session it redirects to the login page, and while the first password is pending, to the password
    change.
  - Pages call it before they read the query string, so that an invalid address also leads to the login page.
  - `requireSession()` only asks for a session. The password change page and its action use it.
- An address that does not exist stays "not found" for everyone who has a session cookie.
- `not-found.tsx`, `error.tsx` and `global-error.tsx` show no data and have no check.
- Without a user the header shows no menu.

## Forced password change

- Whoever logs in with a first password, the admin after the admin setup and every new user, must set a password of
  their own at `/change-password` before doing anything else. Every other address leads there; logging out stays
  possible. The header shows the name and "Log out", but no menu.
- The form asks for the current password, the new one and its repetition. The new password follows the password rules
  and differs from the current one. Each broken rule shows its error at its field; a wrong current password shows
  "Current password is wrong". The form keeps what was entered.
- Better Auth checks the current password and stores the new one. It ends all sessions of the user and starts a new
  one for the browser that made the change, so the other browsers of the user are logged out.
- `mustChangePassword` is cleared only after the password has changed. If that fails, the user changes the password
  once more.
- After the change the user lands on `/folders`. A user without a pending change who opens `/change-password` is led
  there too.

## User list

- Only the admin sees the user list, at `/users`. The header shows the menu entry "Users" to the admin only; for every
  other user `/users` is not found, with and without an action.
- The list shows every user by name, with the time the user was created and the mark "Password change pending" while
  the user still has the first password.
- `listUsers(actor)` in the users service returns `null` for everyone but the admin, without asking the database.

## Creating users

- Only the admin creates users, in the "New user" dialog at `/users?action=create`. No user name has to be reserved
  for an address of its own, so `/users/<name>` stays free for every valid name.
- The admin enters a user name. HippoWiki generates a first password and shows it exactly once, with a copy button,
  for the admin to pass on. The new user has to change it at the first login.
- A generated password is 20 characters long, drawn with the random numbers of `node:crypto` from the letters and
  digits without the ones that are easy to confuse (`0`, `O`, `1`, `l`, `I`).
- The action returns the name and the password in its form state and does not redirect: the password is not part of an
  address or of a stored page, and it is gone after a reload. Once it is shown, the dialog closes only through its
  link "Back to the user list", so that a click next to it or the Escape key cannot lose it.
- `createUser(actor, input)` checks the actor first, then the name, then hashes and writes. For an actor who is not
  the admin it returns `not-allowed`, which the action shows as the not-found page.
- A form cannot choose the password or skip the password change: only the name is read.

## Routes

- `/login`: the login form. Public.
- `/change-password`: the forced password change. It needs a session; without a pending change it leads to `/folders`.
- `/users`: the user list, with the action `create` for the "New user" dialog. For the admin only.
- None of the three has views, and only `/users` has an action; any other action or view shows the not-found page.
- The addresses are built with `loginPath()`, `changePasswordPath()` and `usersPath()` in `src/lib/addresses.ts`.

## Decisions

- Two features, like the two groups in `roadmap.md`: `users` writes accounts with Prisma and the password hashing and
  does not use Better Auth; `auth` is the only code that uses Better Auth, through `getAuth()`. A lint rule keeps
  `@/lib/auth` to the auth service and `src/lib/`.
- A container needs `DATABASE_URL` and `HIPPOWIKI_ADMIN_PASSWORD` and nothing else, so the secret of the session
  cookies is stored in the database instead of a variable.
- Who is calling is found out in the adapters, from the session cookie. What the caller may do is checked in the
  service: a function of the users service that is for the admin only takes the acting user as its first argument
  and decides itself whether it is the admin (`isAdmin()` in `src/features/users/schema.ts`).
- The auth service takes the `Headers` of the request as an argument, because the session lives in a cookie. `Headers`
  is a web standard and not part of Next.js, so the service still works outside a request of Next.js. The functions
  that change the session also return the response headers that set or clear the cookie. In a Server Action the
  `nextCookies()` plugin of Better Auth has already applied them; a caller outside Next.js, such as the integration
  tests, passes them on itself.
- Better Auth logs through the pino logger, and only its errors. Its warnings repeat a refused login, which the auth
  service logs itself with the user name, or say that no base URL is set, which is on purpose: Better Auth uses it
  for its HTTP handler and for links in mails, and HippoWiki has neither.
- A logout that fails throws and shows the error page, because the button has no place for a message and a session
  that could not be ended must not look ended.
- The seed and the tests have a known admin and a known normal user (`prisma/known-users.ts`), both with the password
  change already done. The seed upserts them by name, because an admin that `npm run admin:setup` created has another
  id.

## Current limits

- no rights and roles: everyone who is logged in can read and change all content
- no way to reset a lost admin password; for now the only way is a change directly in the database
- no password reset by the admin for other users, so a lost first password cannot be replaced
- no change of the own password after the forced password change
- no deactivating or deleting of users
- no expiry of first passwords
- no page for each user, and no pages with an author
- no mail, no TOTP, no passkeys, no sign-in with other providers
- no limit on logins per client address
- no audit log
- no HTTP API and no browser client of Better Auth
- no switch for session cookies without `Secure`: a production build needs HTTPS in front of it, or `localhost`
- no return to the address that was asked for after the login
- old rows of `LoginAttempt` are never removed
- the password change is not atomic: Better Auth ends the sessions, stores the password and starts the new session in
  separate statements, and the flag is cleared after them
