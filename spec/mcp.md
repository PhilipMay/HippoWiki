# MCP

The MCP adapter is a thin layer over the services, see [Architecture](architecture.md). This document covers what is
specific to MCP. MCP exposes tools only for now, see [Known Limitations](known-limitations.md).

## Sessions and Principal

- The MCP app runs with `stateless_http=True`. The SDK compares session owners only if the scope holds its own
  `AuthenticatedUser`, so with our principal in the scope any authenticated user holding a session ID would pass. MCP is
  tools only for now, so nothing needs a session.
- MCP tools get the principal through a resolver passed to the server factory. The production resolver reads it from
  the ASGI scope of the HTTP request in the tool context and fails closed if there is none.

## Tool Arguments

The argument model generated by the SDK drops unknown arguments, so `mcp/tools.py` registers every tool through one shared
wrapper that sets `extra="forbid"` on it, and they get a tool error.

## Errors

The [check order](request-checks.md#check-order) defines which tool error each check gives. Routing and schema validation
are reported differently depending on where they fail:

- routing: an unknown tool gets a tool error, and an unknown JSON-RPC method gets a protocol error
- schema validation: malformed JSON gets a protocol error and never reaches a tool. Invalid or unknown tool arguments get a
  tool error, and the tool does not run

MCP keeps the distinction REST makes between 404 and 403 through `not_found` and `forbidden`, and a hidden item gets the
same `NotFoundError` as one that does not exist.

Tool errors are plain text, so `mcp/tools.py` raises a `ToolError` whose message starts with the stable code of the domain
error. A domain error that is not translated would be masked by the SDK as `Error executing tool <name>`.

The SDK puts `Error executing tool <name>: ` in front of the message, so clients find the code right after this text.
Tool errors that the SDK produces itself, for an unknown tool or invalid arguments, have no code.

## Open: Mounting the MCP App

Mounting needs more than the rest of the spec describes so far:

- Lifespan: the `app.py` entry in [Package Layout](package-layout.md) lists only the DB engine, but the session manager must run in the lifespan of the parent app,
  because Starlette does not run the lifespan of mounted apps. Otherwise requests fail with "Task group is not
  initialized" (`streamable_http_manager.py:140-146`, `:185`).
- Path: `streamable_http_path` defaults to `/mcp`, so mounting at `/mcp` results in `/mcp/mcp`
  (`mcpserver/server.py:1291`).
- Host check: by default the SDK enables DNS rebinding protection that allows only localhost hosts and origins
  (`mcpserver/server.py:1164-1168`). Behind the required reverse proxy, real requests would be rejected. The MCP
  transport tests run on a local port and can not notice this, so it needs a setting in the configuration.
- Sessions: with `stateless_http=True` the server sends no session ID, and tools can not send requests to the client, so
  there is no sampling or elicitation (`streamable_http_manager.py:233`). A later feature that needs a session has to bind
  it to the user first.
