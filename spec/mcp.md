# MCP

The MCP adapter is a thin layer over the services, see [Architecture](architecture.md). This document covers what is
specific to MCP. MCP exposes tools only for now, see [Known Limitations](known-limitations.md). The SDK line numbers in
the specification refer to `mcp` 2.3.0.

## Admin Accounts

MCP is only for users who are not admins, see [Auth Concept](auth-concept.md#rules):

- An admin gets HTTP 403 on every MCP request, before any tool runs, see
  [Auth Middleware](auth-middleware.md#admin-accounts-on-mcp). This includes the root admin.
- The adapter has no tools for the [admin operations](auth-concept.md#admin-rights), so a non-admin who calls one gets the
  tool error for an unknown tool.
- `is_admin` is read on every request, so a user who becomes an admin loses MCP access on the next request, and one who is
  no longer an admin gets it back.
- A person who is an admin uses a separate account for connectors, see [AI Agents](authentication.md#ai-agents).

## History and Revert

[History and revert](history-revisions.md) are available only on REST, for every right. The adapter has no tools for them, so
a call gets the tool error for an unknown tool.

## Sessions and Principal

- The MCP app runs with `stateless_http=True`. The SDK compares session owners only if the scope holds its own
  `AuthenticatedUser`, so with our principal in the scope any authenticated user holding a session ID would pass. MCP is
  tools only for now, so nothing needs a session.
- MCP tools get the principal through a resolver passed to the server factory. The production resolver reads it from
  the ASGI scope of the HTTP request in the tool context and fails closed if there is none.

## Tool Arguments

Tools take flat arguments, such as `{"folder_id": "...", "name": "..."}`:

- A tool taking a request model has to be called as `{"req": {...}}`, which would make the name of that parameter part of
  the interface AI clients see.
- Most tools also need an ID that REST carries in the path, so the REST request models would not fit them anyway.
- The tool signatures repeat the fields, and share the field types from `schemas/`, such as `SafeText` and `UtcDatetime`,
  so the validation stays the same as on REST.

`mcp/tools.py` registers every tool through one shared wrapper, which does what the SDK does not:

- The argument model generated by the SDK drops unknown arguments, so the wrapper sets `extra="forbid"` on it, and they
  get a tool error. This uses an SDK internal (`fn_metadata.arg_model`), which a test pins.
- The generated `input_schema` has no `additionalProperties: false`, so the wrapper sets it as well, and clients are told
  about the rule.
- The SDK's invalid-argument error contains `input_value=...` and a pydantic.dev link. The wrapper replaces it with the
  stable code `schema_validation` and the field and reason only, because this text goes straight to AI clients.

## Errors

The [check order](request-checks.md#check-order) defines which tool error each check gives. Routing and schema validation
are reported differently depending on where they fail:

- routing: an unknown tool gets a tool error, and an unknown JSON-RPC method gets a protocol error
- schema validation: malformed JSON gets a protocol error and never reaches a tool. Invalid or unknown tool arguments get a
  tool error, and the tool does not run

MCP keeps the distinction REST makes between 404 and 403 through `not_found` and `forbidden`, and a hidden item gets the
same `NotFoundError` as one that does not exist.

Tool errors are plain text, so `mcp/tools.py` raises a `ToolError` whose message starts with the stable code of the domain
error. A domain error that is not translated would be masked by the SDK as `Error executing tool <name>`.

The SDK puts `Error executing tool <name>: ` in front of the message, so clients find the code right after this text.
The tool error that the SDK produces itself for an unknown tool has no code.

## Serving the MCP App

- Routes: `create_app()` adds the routes of the MCP app to the FastAPI router instead of mounting it, and `POST /mcp` answers
  directly. Mounted at `/mcp`, `POST /mcp` gets a 307 redirect whatever `streamable_http_path` is set to. The `Location` of
  this redirect is built from the request, so behind a TLS proxy it depends on trusting forwarded headers, and MCP clients
  would have to follow it on a POST. `streamable_http_path` keeps its default of `/mcp` (`mcpserver/server.py:1291`).
- Lifespan: the session manager must run in the lifespan of the FastAPI app, because Starlette does not run the lifespan
  of the MCP app. Otherwise requests fail with "Task group is not initialized" (`streamable_http_manager.py:140-146`,
  `:185`).
- Methods: only `POST` reaches the SDK. Every other method gets 405 problem+json with `Allow: POST`, after authentication,
  as MCP allows for a server without a server-initiated stream. Otherwise `GET /mcp` answers 200 `text/event-stream` in
  stateless mode and holds a connection open that nothing uses. A test with real connectors has to check that the target
  clients accept this.
- Host check: by default the SDK enables DNS rebinding protection that allows only localhost hosts and origins
  (`lowlevel/server.py:753`). Behind the required reverse proxy, real requests would be rejected, so the allowed hosts and
  origins are settings (`HIPPOWIKI_MCP_ALLOWED_HOSTS`, `HIPPOWIKI_MCP_ALLOWED_ORIGINS`). A foreign `Host` gets 421 and a
  foreign `Origin` gets 403. The transport tests send these headers explicitly, because a local port would not notice
  otherwise.
- Protocol versions: the SDK sends requests with protocol version `2026-07-28` through a separate path (`handle_modern_request`,
  from `streamable_http_manager.py:194`), before it looks at the stateless setting. The transport tests cover both paths.
- Sessions: with `stateless_http=True` the server sends no session ID, and tools can not send requests to the client, so
  there is no sampling or elicitation (`streamable_http_manager.py:233`). A later feature that needs a session has to bind
  it to the user first.
