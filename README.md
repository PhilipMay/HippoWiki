# HippoWiki

HippoWiki is a knowledge management system, built with Next.js (App Router) and Material UI.

> [!NOTE]
> This was mostly generated by artificial intelligence and carefully piloted by natural intelligence: Claude Opus 5.5 and Claude Fable 5.2 (both on high effort), piloted by Philip May.

## What the prototype can do

The prototype manages wiki pages written in Markdown, organises them in folders and optional tabs and stores them in
PostgreSQL: create, view, edit, move and rename pages, create and rename folders and tabs, and delete pages and
restore them from the deleted pages of their folder. Folders and tabs cannot be deleted yet.

The wiki can only be used after a login, and the admin creates the other users. Everyone who is logged in can read and
change all content, and creates API tokens for scripts and tools on the own account page. AI assistants read the wiki
through an MCP server, with an API token or, for connectors such as the ones of claude.ai and ChatGPT, through OAuth
(see "MCP server").

What is built is described in `spec/`: `spec/content-structure.md`, `spec/pages.md`, `spec/page-deletion.md`,
`spec/users-and-login.md`, `spec/api-tokens.md`, `spec/mcp.md`, `spec/oauth.md` and `spec/container-image.md`.
`CLAUDE.md` lists all spec files.

## Prerequisites

- [nvm](https://github.com/nvm-sh/nvm) with the current Node.js LTS release: `nvm install --lts`. The project's major
  version is pinned in `.nvmrc`.
- [Podman](https://podman.io/) for the development database: `podman machine start`.

## Getting started

```bash
nvm use
cp .env.example .env   # once; .env stays on your machine
npm install            # also generates the Prisma client
npm run db:up
npm run db:migrate     # apply the migrations to the development database
npm run db:seed        # insert a sample folder with two sample pages and the known users
npm run dev
```

The wiki needs a login. After `npm run db:seed`, log in as `alice` with the password `alice-password`, or as the admin
`admin` with `admin-password`. Without the seed, create the admin with `npm run admin:setup` (see "Users").

`.env` can also set the optional `HIPPOWIKI_PUBLIC_URL`, the public address of the wiki, such as
`http://localhost:3000` for `npm run dev`. It is explained in `.env.example`; without it the wiki runs as before.

### Start and stop in one line

Once `.env` exists and the Podman machine runs (`podman machine start`), this line starts everything needed to try the
app: it installs the dependencies, starts the database, applies the migrations, inserts the sample folder with its
pages and starts the development server. It can be run again at any time; existing data is kept and the samples are not
duplicated.

```bash
source ~/.nvm/nvm.sh && nvm use && npm install && npm run db:up && npm run db:deploy && npm run db:seed && npm run dev
```

To spin it down, stop the development server with Ctrl+C and then stop and remove the database container (the data in
the volume is kept):

```bash
npm run db:down
```

`podman machine stop` also stops the Podman machine afterwards.

The app runs at http://localhost:3000.

To start from scratch with an empty database (this deletes all data of the development database):

```bash
npm run db:reset    # remove container and volume, start an empty database
npm run db:deploy   # create the tables
npm run dev
```

`npm run db:seed` adds the sample folder `getting-started` with two sample pages to try this out, and the known users
(see "Users"). `GET /api/health` returns `{ "status": "ok" }` while the database is reachable and status 503
otherwise.

## Database

The development database is PostgreSQL 18 in the Podman container `hippowiki-db`, from the image pinned in
`scripts/Containerfile`. Its data lives in the named volume
`hippowiki-db-data`, and port 5432 is published on localhost only. Database name, user and password are read from
`.env`, and `DATABASE_URL` there must match them.

| Command            | Description                                                                     |
| ------------------ | ------------------------------------------------------------------------------- |
| `npm run db:up`    | Create or start the container and wait until the database accepts connections   |
| `npm run db:down`  | Stop and remove the container; the data in the volume is kept                   |
| `npm run db:reset` | Remove container and volume, then start with an empty database                  |
| `npm run db:psql`  | Open `psql`; pass arguments after `--`, e.g. `npm run db:psql -- -c "select 1"` |
| `npm run db:logs`  | Show the container logs; follow them with `npm run db:logs -- -f`               |

The application accesses the database with [Prisma](https://www.prisma.io/) 7. The schema is in
`prisma/schema.prisma`, the migrations are in `prisma/migrations/` and the connection is configured in
`prisma.config.ts`. The generated client is written to `src/generated/prisma/` and is not checked in.

| Command               | Description                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------- |
| `npm run db:generate` | Regenerate the Prisma client; needed after every change to the schema                       |
| `npm run db:migrate`  | Create and apply a migration from schema changes, e.g. `npm run db:migrate -- --name add-x` |
| `npm run db:deploy`   | Apply all pending migrations without creating new ones                                      |
| `npm run db:seed`     | Insert the sample folder, its pages and the known users from `prisma/seed.ts`               |
| `npm run db:studio`   | Open Prisma Studio to browse and edit the data                                              |

## Users

The login, the wait after failed logins, the forced password change of a first password and the user list of the admin
are described in `spec/users-and-login.md`. There is one admin account, named `admin`; it is created by the seed or by
the admin setup:

- `npm run db:seed` inserts two known users for development (`prisma/known-users.ts`), with the password change
  already done. Running it again gives them these passwords back.

  | User    | Password         |               |
  | ------- | ---------------- | ------------- |
  | `admin` | `admin-password` | the admin     |
  | `alice` | `alice-password` | a normal user |

- `npm run admin:setup` creates the admin account with the password from `HIPPOWIKI_ADMIN_PASSWORD` (8 to 128
  characters), which it reads from the environment or from `.env`, and which the admin has to change at the first
  login. When the admin exists, it does nothing and ignores the variable.

  ```bash
  HIPPOWIKI_ADMIN_PASSWORD=first-password npm run admin:setup
  ```

## MCP server

AI assistants read the wiki through the Model Context Protocol at `/mcp`, acting as a user. A client sends an API token
with the scope `read`, which the user creates on the own account page `/account`, as a bearer token. With Claude Code
and `npm run dev`:

```bash
claude mcp add --transport http hippowiki http://localhost:3000/mcp --header "Authorization: Bearer hw_…"
```

The tools list the folders, list the tabs and pages of a folder and read a page (`spec/mcp.md`).

With `HIPPOWIKI_PUBLIC_URL` set, the wiki is also an OAuth authorization server for MCP clients, such as the connectors
of claude.ai and ChatGPT: the user logs in, approves the connector on a consent page and revokes it on `/account`
(`spec/oauth.md`). With `HIPPOWIKI_PUBLIC_URL=http://localhost:3000` in `.env` and `npm run dev`, Claude Code connects
without a token:

```bash
claude mcp add --transport http hippowiki http://localhost:3000/mcp
```

## End-to-end tests

The end-to-end tests use [Playwright](https://playwright.dev/) with Chromium and live in `e2e/`. Install the browser
once:

```bash
npx playwright install chromium
```

The tests need only the Podman machine (`podman machine start`); they bring their own database:

```bash
npm run test:e2e              # run all end-to-end tests against the development server
npm run test:e2e -- e2e/<name>.spec.ts   # run only the given specs, one path per spec
npm run test:e2e:production   # run them against a production build (next build, next start)
npm run test:e2e:ui           # open the Playwright UI to run and debug tests
npx playwright show-report   # open the HTML report of the last run
```

- Each run starts its own throwaway PostgreSQL container `hippowiki-test-db` (port 5433) and removes it afterwards, also
  when tests fail or the run is stopped with Ctrl+C. The development database is never touched and does not need to
  run.
- Playwright starts its own server on port 3100, so the tests can run next to `npm run dev`.
  `npm run test:e2e:production` builds the app first and takes longer.
- Every test starts logged in as `alice`, with a session that the setup project `e2e/auth.setup.ts` saves once per
  run. `npx playwright test` runs the setup project by itself, also for a single spec. The Playwright UI
  (`npm run test:e2e:ui`) does not: run `auth.setup.ts` there once first, or enable the `setup` project in the project
  filter of the UI, otherwise every test ends on the login page.
- The conventions and helpers of the tests are described in `spec/testing.md`.

## Integration tests

The integration tests run with Vitest against the same throwaway database container as the end-to-end tests and live
in `integration/`. Like the end-to-end tests, they need only the Podman machine:

```bash
npm run test:integration
```

They are not part of `npm run check`. Do not run them at the same time as the end-to-end tests: both use the same
container.

## Unit test coverage

`npm run test:coverage` runs the unit tests, prints a coverage table and writes an HTML report to
`coverage/index.html`. On GitHub, every run of the `unit_tests` workflow shows the coverage in its job summary and
offers the HTML report as the artifact `coverage-report`.

## Container image

The `Containerfile` in the project root builds one image that runs HippoWiki outside the development machine. It
needs only the Podman machine, with at least 4 GiB of memory, because `next build` runs inside it
(`podman machine set --memory 4096` while the machine is stopped):

```bash
npm run image:build   # build the image hippowiki:local for this machine
npm run image:smoke   # check the built image against a throwaway database
```

- What a container needs (`DATABASE_URL`, `HIPPOWIKI_ADMIN_PASSWORD` for the first start, HTTPS in front of it, and
  the optional variables), what it does when it starts and what the smoke test checks is described in
  `spec/container-image.md`.
- To only apply the migrations, start the image with `./image-migrate.sh` as its command:

  ```bash
  podman run --rm --env DATABASE_URL=postgresql://user:password@host:5432/hippowiki hippowiki:local ./image-migrate.sh
  ```

- To only set up the admin, in a running container or in a one-off container:

  ```bash
  podman exec <container> ./image-admin.sh
  ```

  ```bash
  podman run --rm --env DATABASE_URL=postgresql://user:password@host:5432/hippowiki --env HIPPOWIKI_ADMIN_PASSWORD=first-password hippowiki:local ./image-admin.sh
  ```

### Publishing

A published release on GitHub pushes the image to the GitHub Container Registry under the tag name of the release (see
"Publishing" in `spec/container-image.md`). There is no `latest` tag: pull the image by the tag of the release:

```bash
podman pull ghcr.io/<owner>/hippowiki:<tag>
```

A new package is private until its visibility is changed on GitHub, so the host may need to log in to `ghcr.io`
first, with a token that has the `read:packages` scope.
